# Legacy eShop → .NET 8 migration plan

Scope: the three .NET Framework solutions in this repo.

| Solution | Projects |
|---|---|
| `eShopLegacyWebFormsSolution/eShopLegacyWebForms.sln` | `eShopLegacyWebForms` |
| `eShopLegacyMVCSolution/eShopLegacyMVC.sln` | `eShopLegacyMVC`, `eShopLegacy.Utilities`, `eShopPorted` |
| `eShopLegacyNTier/eShopLegacyNTier.sln` | `eShopWCFService`, `eShopWinForms` |

Supporting artifacts in this folder (all regenerated by scripts, do not hand-edit):

- [`inventory.md`](inventory.md) / [`inventory.json`](inventory.json) — static inventory per project: TFM, project style,
  every NuGet package with a .NET 8 disposition, .NET Framework-only assembly references, source-level API usage counts,
  `Web.config`/`App.config` facts (session, modules, WCF endpoints/bindings), WCF operation list, and dead `.cs` files.
  Produced by `python3 tools/net8-migration/inventory.py` (stdlib only).
- [`net8-probe-results.md`](net8-probe-results.md) — the legacy sources actually compiled against .NET 8.
  Produced by `python3 tools/net8-migration/probe_net8.py --dotnet <path-to-dotnet-8>`. Each probe links a slice of the
  legacy source into a throwaway SDK-style project outside the repo, swaps Framework-only packages for their closest
  .NET 8 package, builds, and groups the compiler errors. Nothing in the repo is modified.

> **Timing note.** .NET 8 is LTS but reaches end of support on **10 Nov 2026**. .NET 10 (LTS, Nov 2025) is the
> current LTS. Everything below is written against `net8.0` as requested, but nothing in it is .NET 8-specific; set the
> TFM to `net10.0` if the migration will not finish well before that date. The probes can be re-run against a .NET 10
> SDK unchanged apart from the `tfm` values.

---

## 1. Risk ranking

Ranked by (a) how much code has no .NET 8 equivalent, (b) wire/data compatibility exposure to other systems, and
(c) measured compile breakage. "Errors" are from `net8-probe-results.md`; they measure breadth of coupling, not effort.

| Rank | Project | Risk | Migration type | Headline blocker | Probe evidence |
|---|---|---|---|---|---|
| 1 | `eShopLegacyWebForms` | **Critical** | Rewrite UI, lift domain | WebForms (`System.Web.UI`) does not exist on .NET 8 | 63 errors / 20 files (45× `System.Web.UI`); domain slice: 1 error |
| 2 | `eShopWCFService` | **High** | Re-host (CoreWCF) or replace (REST) | Server-side WCF not in .NET 8; IIS `.svc` + `aspNetCompatibilityEnabled`; EF entities are the wire contract; checked-in WSDL has drifted from the code | 23 errors → **1** after `System.ServiceModel`→`CoreWCF` namespace swap |
| 3 | `eShopLegacyMVC` | **Medium-High** | Port to ASP.NET Core MVC | MVC 5 + Web API 2 + `Global.asax`; `HttpContext.Current.Session` in `_Layout.cshtml`; `BinaryFormatter` wire format on `api/files` | 68 errors / 12 files; domain slice: 1 error |
| 4 | `eShopLegacy.Utilities` | **Medium** (small code, wide blast radius) | Replace serializer | `BinaryFormatter` (SYSLIB0011 is a compile **error** on net8; disabled at runtime) | 2 errors |
| 5 | `eShopWinForms` | **Medium-Low** | Retarget to `net8.0-windows` | Generated WCF proxy relies on `App.config` endpoints, unsupported by the .NET WCF client | 4 errors as-is → **0** after `dotnet-svcutil --sync` regen |
| 6 | `eShopPorted` | **Low-Medium** | Finish the existing 2.2 port | Stale MVC 5 `PicController`; ASP.NET Core 2.2 hosting/EF Core 2.2 runtime breaking changes | 7 errors, all in `PicController.cs` |

Why WCF ranks above MVC despite fewer compile errors: the MVC errors are a well-trodden mechanical mapping
(MVC 5 → ASP.NET Core MVC), while the WCF service is a network contract with unknown external consumers, a
platform gap (no in-box WCF server), and several latent data bugs that a re-host will surface rather than fix.

## 2. Per-project blockers

### 2.1 `eShopLegacyWebForms` — Critical

`net472`, non-SDK Web Application project, `packages.config` (44 packages), IIS Express `http://localhost:50586/`.

**System.Web coupling (no .NET 8 equivalent — this is the whole UI tier)**

- 7 `.aspx`, 2 `.master`, 1 `.ascx`, each with generated `.designer.cs`. Server controls (`asp:ListView`, `asp:DropDownList`,
  validators, `ScriptManager`), postback lifecycle (`Page_Load`, `IsPostBack`, `DataBind()`), `Page.RouteData`,
  `Response.Redirect`. `Catalog/Edit.aspx` (23 server-control hits) and `Catalog/Create.aspx` (22) are the densest.
- `Global.asax.cs : HttpApplication` does startup: Autofac container, `RouteConfig` (`RouteTable` + `MapPageRoute`),
  `BundleConfig` (`BundleTable`/`ScriptManager.ScriptResourceMapping`), DB initializer, and `Session_Start` writing
  `MachineName`/`SessionStartTime` into `HttpContext.Current.Session`.
- DI is **property injection into `Page`** via `Autofac.Integration.Web` (`IContainerProviderAccessor`) — no ASP.NET Core
  analogue; must become constructor injection into page models/components.
- `Web.config`: `sessionState mode="InProc"`, legacy `httpModules` (Application Insights, TelemetryCorrelation, Session
  module), `compilation targetFramework=4.7.2` vs `httpRuntime targetFramework=4.6.1` mismatch (runtime quirks mode is
  4.6.1 today — behaviour to preserve/verify).
- Framework-only references: `System.Web`, `System.Web.Extensions`, `System.Web.Services`, `System.Web.DynamicData`,
  `System.Web.Entity`, `System.Web.ApplicationServices`, `System.EnterpriseServices` (template noise, unused).

**Dependencies**

- Remove (WebForms/System.Web-only): `Autofac.Web`, `Microsoft.AspNet.FriendlyUrls(.Core)`,
  `Microsoft.AspNet.ScriptManager.*`, `AspNet.ScriptManager.*`, `Microsoft.AspNet.Web.Optimization(.WebForms)`,
  `WebGrease`/`Antlr`, `Microsoft.CodeDom.Providers.DotNetCompilerPlatform`, `Microsoft.Net.Compilers`,
  `Microsoft.Web.Infrastructure`, `Microsoft.AspNet.TelemetryCorrelation`, Application Insights `Web`/`WindowsServer`/`Agent.Intercept`.
- Replace: `Microsoft.AspNet.SessionState.SessionStateModule` → ASP.NET Core session + `IDistributedCache`;
  Application Insights → `Microsoft.ApplicationInsights.AspNetCore`; bundling → static assets/LibMan.
- Upgrade: `EntityFramework` 6.2.0 → 6.4.4/6.5.x, `Autofac` 4.9.1 → 8.x, `log4net` 2.0.10 → 2.0.17+, `Newtonsoft.Json` 12.0.1 → 13.0.3.
- Client libs (`bootstrap`, `jQuery`, `Modernizr`, `Respond`, `popper.js`) move out of NuGet to `wwwroot`.

**What is portable** — the `webforms-domain-net8` probe (Models/Services/ViewModel, 11 files, EF6 6.4.4) fails on
exactly one line: `using System.Web.Hosting` in `CatalogDBInitializer.cs` (`HostingEnvironment.ApplicationPhysicalPath`
used to find `Setup/*.csv`/`.zip`). Replace with an injected content-root path and the whole data/service layer builds
on .NET 8. The runtime caveats are EF6-on-.NET-Core ones (see §4).

**Recommendation** — rewrite the UI as Razor Pages (closest page-centric model; forms/validation map cleanly) on top of
the lifted domain layer. Blazor Server is the alternative if a component model is wanted; it is a bigger conceptual jump
and not required by anything in this app. There are only ~5 functional pages (list/paging, details, create, edit,
delete) so a rewrite is bounded.

### 2.2 `eShopWCFService` — High

`net461`, non-SDK Web Application project (assembly name `WcfService1`), hosted by IIS/IIS Express at
`http://localhost:62314/CatalogService.svc`.

**WCF surface**

- One contract, `ICatalogService : IDisposable`, 10 operations: `FindCatalogItem`, `GetCatalogBrands`,
  `GetCatalogItems(int, int)`, `GetCatalogTypes`, `GetAvailableStock(DateTime, int)`, `CreateAvailableStock`,
  `CreateCatalogItem`, `UpdateCatalogItem`, `RemoveCatalogItem`, `GetDiscount(DateTime)`.
- Endpoints: `basicHttpBinding` at the base address + `mexHttpBinding` at `mex`; `serviceMetadata httpGetEnabled/httpsGetEnabled`;
  `protocolMapping https→basicHttpsBinding`; `serviceHostingEnvironment aspNetCompatibilityEnabled="true"`.
- Data contracts are the **EF6 entities themselves** (`[DataContract]` + `[Table]`/`[Key]`/`[DatabaseGenerated]`/navigation
  properties on `CatalogItem`, `CatalogBrand`, `CatalogType`, `CatalogItemsStock`, `DiscountItem`).
- **Contract drift:** the checked-in client metadata (`CatalogService.xsd`) declares `brandIdFilter`/`typeIdFilter` as
  `nillable="true"` → the generated proxy exposes `int?`, while the service code takes `int` and uses `0` as "no filter".
  The WSDL in source control is therefore not the contract that is running; any wire-compatibility test must be built from
  the live service's `?wsdl`, not from the repo copy.
- `IDisposable` on a service contract is not a wire concept; it only leaks EF context lifetime into the contract.

**System.Web coupling** — code-level coupling is nil (the five `using System.Web;` lines are unused), but hosting coupling
is total: `.svc` activation, `aspNetCompatibilityEnabled`, IIS Web Application project targets, `Web.config`
`system.serviceModel`. None of that exists on .NET 8.

**Dependencies** — only `EntityFramework` 6.1.3 (→ 6.4.4+). Framework references `System.Data.Entity.Design` and
`System.EnterpriseServices` are unused template references; drop them.

**Latent data bugs that a migration will surface** (not blockers, but must be decided): IDs allocated as `Max(id)+1`
(race under concurrency); list operations materialise whole tables before filtering; navigation properties populated
by hand after the query; single EF context per service instance.

**Probe result** — with CoreWCF 1.5.2 + EF6 6.4.4 the service/contract/models compile after a single mechanical change
(`System.ServiceModel` → `CoreWCF` namespace); the one remaining error is an unused `using System.ServiceModel.Web`.

**Decision required — two viable paths**

| | A. Re-host on CoreWCF (`net8.0`) | B. Replace with REST (`eShopModernizedNTier/src/eShopCoreAPI`, already `net8.0`) |
|---|---|---|
| Wire compatibility | Same SOAP contract & URL; existing clients unchanged | Breaking; every client must change |
| Effort | Small (probe: 1 error) + hosting/config in code | API already exists on `main`; client work instead |
| Long-term | CoreWCF is community-supported (.NET Foundation), not part of .NET | Mainstream ASP.NET Core |
| Use when | Unknown/external SOAP consumers exist | All consumers are in this repo (only `eShopWinForms` today) |

Recommended: **A first, then B** — re-host on CoreWCF behind the same URL so the server can move independently of any
client, then migrate clients to REST and retire the SOAP endpoint once consumer telemetry shows zero traffic.

### 2.3 `eShopLegacyMVC` — Medium-High

`net472`, non-SDK MVC project, **mixed** `packages.config` + `PackageReference` (48 packages), 10 binding redirects,
IIS-hosted.

**System.Web coupling**

- `Global.asax.cs : HttpApplication`: Autofac (`DependencyResolver.SetResolver` + `GlobalConfiguration.Configuration.DependencyResolver`),
  `GlobalConfiguration.Configure(WebApiConfig.Register)`, `AreaRegistration`, `GlobalFilters`, `RouteTable`, `BundleTable`, DB init,
  and `Session_Start` via `HttpContext.Current.Session`.
- Two controller stacks: MVC 5 (`System.Web.Mvc.Controller`: `CatalogController`, `PicController`, `Controllers/Api/CatalogController`)
  and Web API 2 (`ApiController`: `WebApi/BrandsController`, `WebApi/FilesController`) returning `IHttpActionResult`/`HttpResponseMessage`.
  ASP.NET Core unifies these, so routing must be re-expressed (`{controller}/{action}/{id}` default + attribute routes + `api/{controller}/{id}`).
- `PicController` uses `Server.MapPath("~/Pics")` → `IWebHostEnvironment.WebRootPath`/`ContentRootPath`.
- Views: `_Layout.cshtml` reads `HttpContext.Current.Session["MachineName"]`; `@Scripts.Render`/`@Styles.Render` (System.Web.Optimization);
  HTML helpers mostly carry over (`Html.ActionLink`, `EditorFor`, `ValidationMessageFor`, `AntiForgeryToken`) but should move to Tag Helpers.
- `BrandsController` imports `System.Runtime.Remoting.Messaging` (not on .NET 8; unused import — delete).

**Dependencies** — replace MVC 5 / Web API 2 / Razor 3 / WebPages / `Microsoft.AspNet.WebApi.WebHost` with the
`Microsoft.AspNetCore.App` shared framework; `Autofac.Mvc5` + `Autofac.WebApi2` → `Autofac.Extensions.DependencyInjection`;
remove bundling/CodeDom/compiler/`Microsoft.Web.Infrastructure`; drop the ~12 `System.*` compat packages (in-box on net8).
The repo's `Convert-ToPackageReference.ps1` is not needed once the project is SDK-style.

**BinaryFormatter wire format** — `GET api/files` (`WebApi/FilesController`) returns a `BinaryFormatter` stream of
`FilesController+BrandDTO`. That payload embeds the .NET Framework assembly/type name, so it cannot be consumed by a
renamed/retargeted assembly anyway, and `BinaryFormatter` is disabled in ASP.NET Core on .NET 8 (and removed in .NET 9).
The endpoint's format **must** change (JSON); any consumer must be found and migrated in lockstep.

**Portable** — `mvc-domain-net8` probe: same single `System.Web.Hosting` error as WebForms. The MVC and WebForms
Models/Services are near-identical; they should become **one** shared library.

### 2.4 `eShopLegacy.Utilities` — Medium

Two files, `net461`, no packages. `Serializing.SerializeBinary/DeserializeBinary` use `BinaryFormatter`
(compile error SYSLIB0011 on net8). Referenced by both `eShopLegacyMVC` and `eShopPorted` — it is the only compile-time
project reference shared between projects, so it gates both. Replace with `System.Text.Json` (or keep a `net472`-only
build of the old method behind `#if NETFRAMEWORK` for the transition window). Security note: `DeserializeBinary` on an
untrusted stream is a known RCE sink; that alone justifies removing it before or during the migration.

### 2.5 `eShopWinForms` — Medium-Low

`net47` WinExe, non-SDK, 3 packages (`EntityFramework` 6.1.3 — unused by the client code path, `Microsoft.AspNet.WebApi.Client`
5.2.3, `Newtonsoft.Json` 6.0.4), ClickOnce bootstrapper metadata, `System.Deployment` reference (no code uses it).

**WCF client surface** — Connected Service `eShopServiceReference` (WSDL + 4 XSD + `Reference.svcmap`), generated
`Reference.cs` with `ClientBase<ICatalogService>` exposing 10 sync + 10 `Task` operations. `Program.Main` does
`new eShopServiceReference.CatalogServiceClient()` which resolves the endpoint from `App.config`
(`BasicHttpBinding_ICatalogService` → `http://localhost:62314/CatalogService.svc`).

**Probe results**

- As-is on `net8.0-windows` with `System.ServiceModel.Http/Primitives` 8.0.0: 4 errors, all in `Reference.cs` — the
  `ClientBase(string endpointConfigurationName)` constructors; the .NET WCF client does not read `system.serviceModel` config.
- Regenerating the proxy from the **checked-in** WSDL/XSD with `dotnet-svcutil 2.1.0`: default (async-only) output leaves
  8 errors because `CatalogController` calls the synchronous methods; with `--sync` the whole client (Views, Controllers,
  designer, resx) **builds with 0 errors**.

**Remaining work** — construct the client in code (`new CatalogServiceClient(binding, new EndpointAddress(uri))` with the
URI from `appsettings`/settings); move blocking calls on the UI thread to the generated `Task` methods (`async` event
handlers); `CatalogView.cs` loads images from `Environment.CurrentDirectory + "\..\..\Assets\Images\Catalog\"` — replace
with `AppContext.BaseDirectory` + copied content; ClickOnce publish works on .NET 8 but the profile must be recreated;
Windows-only by definition (`System.Drawing`, WinForms). Seven UWP-flavoured `Helpers/*.cs` files on disk are not in the
csproj — delete, do not port. Existing prior art: `eShopModernizedNTier/src/eShopWinForms` already targets `net6.0-windows`
(out of support since Nov 2024) with `System.ServiceModel.*` 4.8.0 — retarget it to `net8.0-windows` / 8.0.x packages.

### 2.6 `eShopPorted` — Low-Medium

SDK-style but `net461` + ASP.NET Core 2.2 + EF Core 2.2.6 — both out of support. It also references `Autofac.Mvc5`,
`WebGrease` and `Antlr`, which transitively pull MVC 5 onto `net461`; that is the only reason its stale
`Controllers/PicController.cs` (`using System.Web.Mvc`, `HttpStatusCodeResult`, `HttpNotFound`) compiles today.

Retargeted to `net8.0` with EF Core 8 / Autofac.Extensions.DI 9 it fails **only** in `PicController.cs` (7 errors). After
fixing that, the runtime breaking changes from 2.2 → 3.0+ still apply and are not caught by the compiler:
`ConfigureServices` returning `IServiceProvider` (unsupported with the generic host → use `UseServiceProviderFactory(new AutofacServiceProviderFactory())`),
`services.AddMvc()` + `app.UseMvc(routes => …)` (needs endpoint routing: `AddControllersWithViews` + `MapControllerRoute`),
`IHostingEnvironment` → `IWebHostEnvironment`, EF Core 3.0 removal of client-side evaluation, and Microsoft.Data.SqlClient's
`Encrypt=true` default. It still links `eShopLegacy.Utilities` (`BinaryFormatter`).

## 3. Target architecture and sequencing

Principle: strangler-fig per solution, **shared/leaf code first, clients before servers, compatibility layers before
rewrites**. Each phase is independently shippable and has an exit gate.

```text
Phase 0  Baseline & safety net ─────────────────────────────────────────────┐
Phase 1  eShop.Catalog.Core (shared domain, multi-target) + Utilities fix   │ gates everything
Phase 2  eShopWinForms → net8.0-windows (still calls legacy WCF)            │ independent of server
Phase 3  eShopWCFService → CoreWCF on net8.0 (same SOAP contract/URL)       │
Phase 4  eShopLegacyMVC → ASP.NET Core 8 MVC (YARP strangler)               │ builds shared web host
Phase 5  eShopLegacyWebForms → Razor Pages on the Phase 4 host              │ highest risk, last
Phase 6  EF6 → EF Core 8, retire SOAP, retire legacy apps                   ┘
```

**Phase 0 — Baseline** (prerequisite for every gate)
- Windows CI job building all three `.sln` with MSBuild/VS Build Tools today (there is none; nothing on Linux can build them).
- Characterisation tests: HTTP golden tests for every MVC/WebForms route (status, key HTML, `api/*` JSON), a SOAP
  replay suite recorded from the **live** `CatalogService.svc?wsdl` (not the drifted repo WSDL), and DB-state checks for
  create/edit/delete. The repo has no test projects today.
- Inventory external consumers: IIS logs / App Insights for `CatalogService.svc` and `api/files`.
- Decide TFM (`net8.0` vs `net10.0`, see timing note).

**Phase 1 — Shared domain + utilities**
- Merge MVC and WebForms `Models`/`Services`/`ViewModel` into one SDK-style `eShop.Catalog.Core` multi-targeting
  `net472;net8.0`; replace `HostingEnvironment.ApplicationPhysicalPath` with an injected content-root path; EF6 6.4.4+/6.5
  with a code-based `DbConfiguration` (see §4). Legacy apps reference it, proving no behaviour change on .NET Framework.
- `eShopLegacy.Utilities`: replace `BinaryFormatter` with `System.Text.Json`; switch `api/files` to JSON (coordinated with
  consumers from Phase 0).
- Gate: legacy apps pass Phase 0 suites referencing the new library; `webforms-domain-net8`/`mvc-domain-net8` probes → 0 errors.

**Phase 2 — WinForms client**
- SDK-style `net8.0-windows`, `UseWindowsForms`; proxy regenerated with `dotnet-svcutil --sync` from the live WSDL;
  endpoint built in code from settings; images via `AppContext.BaseDirectory`; async UI calls.
- It keeps talking to the **legacy** WCF service (`basicHttpBinding` is supported by `System.ServiceModel.Http`), so it
  ships without waiting for any server work. Start from `eShopModernizedNTier/src/eShopWinForms`.
- Gate: manual/UI-automation smoke on Windows against legacy WCF; ClickOnce publish installs and updates.

**Phase 3 — WCF service on CoreWCF**
- ASP.NET Core host + `CoreWCF.Http` (+ `CoreWCF.Primitives`), `basicHttpBinding` at `/CatalogService.svc`, WSDL via
  `ServiceMetadataBehavior`; namespace swap `System.ServiceModel` → `CoreWCF`; drop `IDisposable` from the contract
  (scoped EF context via DI instead); keep entity/`[DataContract]` shapes byte-identical for now.
- Replace `aspNetCompatibilityEnabled` (nothing in code needs it — verify with the SOAP suite).
- Gate: SOAP replay suite green against both old and new hosts; WSDL diff empty (or reviewed); WinForms from Phase 2
  works against the new host by changing only the endpoint URI.

**Phase 4 — MVC on ASP.NET Core**
- New `net8.0` web host (evaluate `eShopModernized/src/eShopCoreModernized`, already `net8.0` on `main`, vs finishing `eShopPorted`).
- YARP in front: route migrated paths to the new app, fall back to the legacy IIS app. Use
  `Microsoft.AspNetCore.SystemWebAdapters` remote session so `MachineName`/`SessionStartTime` survive across both.
- Map MVC 5 + Web API 2 controllers onto one ASP.NET Core controller model; `Server.MapPath` → `IWebHostEnvironment`;
  bundling → static files; `HttpContext.Current.Session` in `_Layout` → injected `IHttpContextAccessor`/view component.
- Gate: route-level golden tests green for each route moved behind YARP; `mvc-full-net8` equivalent project builds with 0 errors.

**Phase 5 — WebForms rewrite**
- Razor Pages in the Phase 4 host (shared layout, DI, config, EF, telemetry, auth), one page at a time behind YARP:
  `Default` (list/paging) → `Details` → `Delete` → `Create`/`Edit` (validators + dropdown binding are the bulk).
- Autofac property injection → constructor injection; `RouteData`/`MapPageRoute` → `@page "{id:int}"`.
- Gate: per-page golden tests + visual diff; functional parity checklist signed off.

**Phase 6 — Consolidation**
- EF6 → EF Core 8: `CreateDatabaseIfNotExists` + SQL scripts → migrations; the custom Hi/Lo sequence generator →
  `UseHiLo("catalog_hilo")` / `catalog_brand_hilo` / `catalog_type_hilo` (same sequences, verify increment); WCF `Max(id)+1` → identity/sequence.
- Move WinForms from SOAP to REST (`eShopCoreAPI`) if Phase 0/3 telemetry shows no external SOAP consumers; retire CoreWCF.
- Decommission IIS apps and YARP fallbacks.

## 4. Cross-cutting risks

| Risk | Where | Mitigation |
|---|---|---|
| EF6 on .NET 8 does not read `<entityFramework>`/`<connectionStrings>` from `Web.config` the same way | all three data layers (`name=CatalogDBContext`, `name=EntityModel`) | Code-based `DbConfiguration` (`SetProviderServices("System.Data.SqlClient", SqlProviderServices.Instance)`) and explicit connection strings from `IConfiguration`; EF 6.5 adds `Microsoft.Data.SqlClient` provider |
| LocalDB connection strings | every `Web.config` | Container/CI SQL Server; config per environment |
| `BinaryFormatter` payloads | `api/files` (MVC, Ported) | JSON; consumer migration in Phase 1 |
| Session state InProc | WebForms, MVC | SystemWebAdapters remote session during coexistence; distributed cache after |
| `httpRuntime targetFramework=4.6.1` quirks vs 4.7.2 compilation | WebForms, MVC | Golden tests capture current behaviour (encoding, validation) |
| WSDL drift (`int?` vs `int`) | WCF ↔ WinForms | Regenerate from live service; add a CI WSDL-diff check |
| Newtonsoft.Json 6.0.4 / 12.0.1 | WinForms, WebForms | 13.0.3 or System.Text.Json |
| ASP.NET Core 2.2 / EF Core 2.2 / .NET 6 prior art is out of support | `eShopPorted`, `eShopModernizedNTier/src/eShopWinForms` | Treat as reference only; retarget |

Built locally with .NET SDK 8.0.425 (`dotnet build`, 0 errors each):
`eShopModernized/src/eShopCoreModernized` (`net8.0`, EF Core 8), `eShopModernizedNTier/src/eShopCoreAPI` (`net8.0`, EF Core 8, Swagger),

## 6. Assumptions

- "The three legacy solutions" are the `eShopLegacy*` `.sln` files; `eShopModernized*` are prior art, not in scope.
- SQL Server stays the database; Windows remains the WinForms runtime.
- External consumers of `CatalogService.svc` and `api/files` may exist (unknown from the repo), hence the CoreWCF-first
  and consumer-inventory steps.
- Package versions used in the probes (EF6 6.4.4, CoreWCF 1.5.2, System.ServiceModel 8.0.0, Autofac 8.0.0, EF Core 8.0.8,
  log4net 2.0.17, dotnet-svcutil 2.1.0) were chosen as known .NET 8-compatible versions for measurement, not as final pins.

## 7. Validation performed and limits

- `inventory.py` output cross-checked by hand against every `.csproj`, `packages.config`, `Web.config`/`App.config`,
  `ICatalogService.cs` and the generated `Reference.cs`.
- `probe_net8.py`: 10 compile probes against .NET SDK 8.0.425 on Linux (results in `net8-probe-results.md`).
- **Not done:** the legacy solutions were not built on .NET Framework (no Windows/MSBuild web targets on this Linux host);
  probes are compile-only — nothing was run, no database was attached, WinForms was compiled with
  `EnableWindowsTargeting` but not launched; the WSDL drift finding is from source, not from a running service.
