# eShop Strangler Fig Migration - Completion Documentation

## Migration Overview

The strangler fig migration from .NET Framework to .NET Core has been completed successfully. This document outlines the final architecture and operational procedures.

## Final Architecture

### Traffic Routing
- **API Endpoints** (`/api/*`): 100% .NET Core (port 5002)
- **Catalog Endpoints** (`/Catalog/*`): 100% .NET Core (port 5002)
- **Health Checks** (`/health*`): .NET Core (port 5002)
- **Legacy Endpoints**: Modernized .NET Framework (port 5001)

### Service Ports
- **Legacy .NET Framework**: localhost:5000 (decommissioned)
- **Modernized .NET Framework**: localhost:5001 (remaining functionality)
- **.NET Core**: localhost:5002 (primary catalog service)

## Monitoring and Health Checks

### Health Endpoints
- `/health/live`: Liveness - process is up (no dependency checks); used by the Docker `HEALTHCHECK`
- `/health/ready`: Readiness - catalog database / mock data and Azure Blob Storage (when enabled); returns 503 when unhealthy
- `/health`, `/health/detailed`: Full report of every check with service, version, deployment track and instance
- `/api/health`, `/api/health/detailed`: Existing API contract, now backed by the same readiness checks
- `/gateway/health` (nginx): gateway liveness; the `X-Migration-Stage` response header reports the active stage

### Structured Logging
- JSON console logs in containers/production (`Logging:Console:FormatterName=json`), single-line text in Development
- One `RequestCompleted` event (EventId 1000) per request with method, path, status, latency and endpoint
- Every log scope carries `CorrelationId`, `ServiceName`, `ServiceVersion` and `DeploymentTrack`
- `X-Correlation-ID` is accepted from the caller (or generated by nginx) and echoed with `X-App-Version` and `X-Deployment-Track`
- Readiness transitions are logged every 30s by a health publisher (EventId 2000/2001)
- nginx writes JSON access logs with `upstream_addr`, `upstream_status`, `deployment_track`, `app_version` and `migration_stage`, so per-backend error rate and latency can be compared for each canary stage

### Application Insights
- Custom telemetry for migration tracking
- Performance monitoring and comparison
- Error tracking and alerting
- Live metrics stream enabled

## Traffic Migration Strategy

The migration uses nginx upstream weighting for gradual traffic distribution:

### Migration Phases
1. **25% Phase**: `nginx-25percent.conf` - 25% to .NET Core, 75% to .NET Framework
2. **50% Phase**: `nginx-50percent.conf` - 50% to .NET Core, 50% to .NET Framework
3. **75% Phase**: `nginx-75percent.conf` - 75% to .NET Core, 25% to .NET Framework
4. **100% Phase**: `nginx-100percent.conf` - 100% to .NET Core

### Migration Script
Use `./migrate-traffic.sh {25|50|75|100}` to apply each phase with automatic health monitoring. Each stage:
1. Refuses to start unless `.NET Core /health/ready` is healthy
2. Backs up and applies the stage config, runs `nginx -t` + reload, and confirms the gateway reports the new `X-Migration-Stage`
3. Probes `.NET Core /health/ready`, gateway `/api/health` and a synthetic `/Catalog/` request every `MONITOR_INTERVAL` seconds
4. Restores the previous config automatically after `MAX_CONSECUTIVE_FAILURES` failed probes or more than `MAX_FAILURE_PERCENT` failures overall (exit code 4)

`./migrate-traffic.sh status` shows the active stage and health; `./migrate-traffic.sh rollback` restores the most recent backup.

To exercise the stages locally on Linux, start `docker compose -f docker-compose.canary.yml --profile baseline up -d --build --wait` (SQL Server, the .NET Core app on :5002, a stand-in for the .NET Framework app on :5001, and the nginx gateway) and run the script with:
```bash
export NGINX_TEST_CMD="docker compose -f docker-compose.canary.yml exec -T gateway nginx -t"
export NGINX_RELOAD_CMD="docker compose -f docker-compose.canary.yml exec -T gateway nginx -s reload"
./migrate-traffic.sh 25
```
